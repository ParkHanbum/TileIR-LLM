Methods / avoid misleading comparisons

One experiment,
one defensible claim.

Fixed workload

  • GPU: NVIDIA RTX 4080, 16 GB class. Runs share a desktop environment; GUI contention is a limitation.
  • Model: Qwen3.5-4B, matching checkpoint revision and BF16 precision.
  • Batch 32, prompt length 53, generation length 16, greedy selection. The current correctness workload repeats the same prompt across rows.
  • Native inference consumes prompt IDs and checkpoint weights. Its generated ID feeds the next decode step; expected IDs or intermediate reference tensors are not inference inputs.
  • vLLM reference version: 0.32.0. Pin the exact revision, configuration, prompt IDs, executable and input hashes for a replay.

What “token-only” means

No detokenization or public logprob output. It does not mean “no validation overhead”: the measured native path retains finite checks, canaries, bounds checks and host feedback. Those costs remain in its request timing.

Primary wall-time boundary

outside timer: prepare resident engine → warmup
inside timer:  request reset/setup → prefill → 15 decode steps
               → final CPU token IDs → request cleanup/completion
outside timer: compare token IDs → write logs → engine shutdown

Weights and prepared modules stay resident. Independent requests do not reuse computed prompt results or KV cache. Prefix caching is off. Request state is freshly initialized. The two engines execute serially, never simultaneously on the GPU.

Repetition and correctness

The initial paired test used N,V,V,N process blocks, each with 2 warmup and 6 timed requests. Every request produced 512 tokens; all 16,384 IDs across warm and timed requests matched. Timed-run medians are reported separately from warmup. The guard experiment used A,B,B,A with the same repetition counts.

Attribution rules

  1. Change one runtime behavior; preserve numerical kernels and workload.
  2. Retain fail-closed semantics, or explicitly state any changed safety contract.
  3. Qualify failures/negative cases before full-model timing.
  4. Measure unprofiled; collect traces separately. Node-level CUDA Graph tracing can add overhead.
  5. Do not add host API wait time to overlapping GPU execution time. Synchronous copies and deallocation may include waiting for prior work.
  6. Report actual exits, cleanup, recovery, and failure cases. A successful comparison is not just a plausible-looking text completion.

Known scope limits

The native path currently targets a fixed non-EOS workload. General EOS behavior, broader prompts, sampling policies and public logprob equivalence are not established by these tests. “TileIR-based” describes the model compute implementation; CUDA Driver allocation, transfer and memset infrastructure still exists. No claim is made that every physical device operation originates in a TileIR numerical kernel.
