# Public source explanation of actual top5 tie mismatch

Installed Torch 2.13.0+cu130 records git cf30153c4c131c8164ee7798e5022d810682e2cb. Public TensorTopK.cpp, TensorTopK.cu and Sort.cu were fetched from raw.githubusercontent.com/pytorch/pytorch at that exact revision. Installed SortUtils.cuh, SortingRadixSelect.cuh, Sort.h and CuTeDSL eligibility source were read/copied. No proprietary binary analysis or GPU work.

## Dispatch inference, not a measured kernel binding
CuTeDSL topk requires FP32 and k in {16,32,64,128,256,512,1024}; BF16 k=5 falls through. On NVIDIA, should_use_sort and should_use_warp_topk return false. For 32 rows and width248320, should_use_multiblock is true (21..40 rows and width>=10000). After selection, sorted=True uses small sort because k5<=4096; unstable sort_size<=32 selects SmallBitonicSort with32 slots,16 threads,2 items/thread. These are source-derived conditions; matching the installed git string does not independently prove which loaded binary kernel ran or exclude a vendor build patch.

## Why neither ascending nor descending index is the tie contract
mbtopk gather uses a radix-selected fifth value. It writes strictly-above-threshold items in ascending source-index order through block prefix counts and per-loop exclusive scan, then earliest threshold-equal indices fill the remaining positions. The five unsorted survivors occupy slots0..4, with27 invalid slots. SortUtils bitonicSwap compares values only: swap=(comp(A,B)&&validA)||!validB; it exchanges when swap==direction. Equal values can exchange in particular network stages. The resulting permutation depends on input positions and the whole network, not a universal index tie direction.

CPU emulation of this gather ordering and exact32-slot network reproduced all160 IDs in the actual failing32-row bank. Existing ascending-index candidate differs at64 positions. Representative row: values [21,20.625,17.875,17.875,17.75], native IDs [6891,7836,3050,854,52652], candidate [6891,7836,854,3050,52652]. Both original isolated first/last banks also match the emulator exactly. This is evidence for the explanation, not new GPU qualification. API torch.topk does not guarantee tied index stability across invocations/configurations/versions.

## Compatible implementation proposal
Keep a generic top5 selection algorithm, but produce the same five-survivor set using BF16 radix ordering, not an ad hoc index reversal. Reconstruct pre-sort order as above-threshold survivors ascending index followed by threshold-equal selected indices ascending index. Run the exact public32-slot validity-aware bitonic network in TileIR. Preserve public PyTorch license/copyright for adapted network. A block-top5 union is sufficient to recover the survivors if its ordering uses the same radix keys and earliest-index tie selection. Then validate original2 banks + failing bank and synthetic tie patterns including cutoff ties and many ties before full16 integration. Do not weaken raw gates or adopt merely because CPU emulation fits one bank.

Signed zero warning: BF16 TopKTypeConfig converts raw bits using sign-dependent xor; +0 and -0 have distinct radix keys even though the final floating comparator regards them equal. The current CPU emulator uses numerical threshold comparison and is justified only on these positive-top5 banks; it is NOT a complete signed-zero/NaN emulator. A general faithful adapter must implement bit-key thresholding or explicitly reject that boundary. NaN/Inf stay outside the existing finite-only contract. No overall topk ABI/version-independent tie guarantee is promised.

Existing model HOLD and all previous source remain unchanged. CPU emulation uses saved tensors only, CUDA hidden and is_initialized=False. No new CUDA query/init/compile/launch/lock.
