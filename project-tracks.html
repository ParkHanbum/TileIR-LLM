TileIRBLAS and the TileIR inference runtime are separate engineering tracks. They can advance in parallel, but only a fresh matched end-to-end experiment establishes their combined effect.

This page defines how work and evidence are organized. It announces no new implementation, qualification pass, performance gain or completed benchmark.

Track A: TileIRBLAS

Question: does the actual exported TileIR kernel implement the required operation correctly and perform competitively under the same mathematical and memory-layout contract?

  • Record the operation, M/N/K or other dimensions, dtype, accumulation behavior, strides/layout, alignment requirements, output policy and launch ABI.
  • Validate numerical results and supported boundary cases; check ownership and error behavior where they belong to the interface.
  • Pin source/export identity, numerical CUBIN and launch configuration. Keep host compile settings distinct from GPU compilation.
  • Benchmark the same logical workload and checked layout. Report CUDA-event time separately from profiler kernel time, cache-bank controls and end-to-end wall time.
  • Do not treat a standalone torch.mm control as proof of the kernel selected inside vLLM, or substitute a different ABI directly into the engine.

Handoff: a versioned kernel/interface contract, validation evidence, matched kernel measurement and explicit supported shapes. Unsupported or untested inputs remain labeled as such.

Evidence anchors: historical standalone controls and current export/shape scope audit. The former does not qualify every current engine GEMM.

Track B: TileIR inference runtime

Question: does the runtime provide the required model execution flow, and where does its request lifecycle differ from the reference runtime?

  • Separate engine initialization, request setup, prefill, decode, token feedback, cleanup and final completion.
  • Compare actual module/function logic and dispatch contracts, not only aggregate profiles or library names.
  • Isolate host preparation, allocation/retirement, cache ownership, synchronization, validation and scheduling changes while pinning numerical kernels when the experiment permits.
  • Preserve correctness, dynamic ownership checks, failure semantics and completion boundaries. A faster invalid or less-checked path is not an equivalent implementation.
  • Record actual host flags, effective runtime settings and relevant dispatch observations. Distinguish observed traces from incomplete or unavailable traces.

Handoff: a versioned runtime configuration, lifecycle/correctness evidence, isolated A/B and an explicit description of which kernel set was held fixed.

Evidence anchors: host compiler A/B, guard success path and prepared launch metadata. These are distinct experiments, not cumulative speedups.

Native-only integration evidence: gate/up prefill S64 model A/B is a one-module request experiment, separate from standalone qualification. It does not update the matched native-vLLM checkpoint.

Matched end-to-end checkpoints

Question: after integrating explicitly qualified versions, how does the complete native request compare with vLLM under the stated conditions?

  • Pin model/checkpoint, input token IDs, precision, batch/prompt/generation sizes, sampling and stopping policy.
  • Pin the native runtime and selected module versions, plus reference artifacts and effective settings. Record reservation differences rather than claiming identical allocation.
  • Use a shared request-wall-time definition, separate warmup from timed runs, and serialize competing GPU experiments.
  • Compare tokens generated by the engines themselves, not injected reference decode tokens or intermediate tensors. State the exact tested accuracy scope and actual exit/recovery outcomes.
  • Publish the new matched result independently. Do not multiply track-level gains or divide a fresh native median by an old reference median.

The latest published matched checkpoint in this documentation is E08. Its measured configuration is not automatically the result for any later diagnostic or candidate.

Parallel work, serialized evidence

Independent source analysis, interface work, test preparation and documentation can proceed concurrently in the two tracks. Integration changes should name their dependency versions and preserve an identifiable baseline. Shared-device performance experiments must remain serialized and retain independent receipts, so parallel development does not turn into competing GPU timings.

A candidate progresses through proposed → implemented → qualified → measured → integrated only when evidence supports each step. These are workflow labels, not assertions that any currently discussed candidate has reached a particular state. Cross-track changes require an explicit integration checkpoint rather than implicit promotion of one track's result.
