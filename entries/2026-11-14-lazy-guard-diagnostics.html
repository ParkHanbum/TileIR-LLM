798.036 ms less per request: approximately 14.00% reduction, 1.163× speedup. This is a native-only A/B with the same optimized host compiler setting. vLLM was not rerun.

Precisely one success-path change

The candidate still inspects every required canary byte in the same order and stops on the first failure. Instead of eagerly constructing an error message while each byte is successfully checked, it constructs the exact existing message only when the check fails.

Baseline:  build diagnostic message → compare guard byte
Candidate: compare guard byte → if failure, build same message

Unchanged: checked bytes + order + first failure + error text
           CUDA work + fences + allocation + numerical CUBINs

This does not disable guards, sample fewer bytes or change their completion boundaries. Both host builds use -O3. The CUDA calls, canary byte set/order, fences, allocations and CUBINs are unchanged.

Correctness and failure behavior

  • 32 requests × 512 = 16,384 generated IDs exact.
  • Same 9,409 dispatches per request and unchanged aggregate operation counts.
  • GPU qualifier: 10 contexts and 8 negative cases, checking failure handling rather than only valid inputs.
  • All five children (qualifier plus four model blocks) and the outer launcher actually exited 0.
  • Independent recovery passed with no remaining experiment child.

The fixed native workload and warm request timer follow the measurement contract. This change is in the CPU guard-checking success path, not the model numerical kernels or TileIR GPU optimization passes.

What we can now conclude

The integrated A/B establishes a measurable cost for eager diagnostic construction in this runtime. Preserving the failure message and checking contract does not require paying that construction cost for each successful byte.

The earlier standalone CPU guard replay was useful for choosing a hypothesis, but its workload and timing are not the engine measurement. Its reported millisecond difference cannot be subtracted from these request times or used to attribute the full 798.036 ms reduction.

No new native-vLLM ratio is reported. Do not divide this candidate's time by a historical vLLM time and call it a matched comparison, or multiply separate experiments' speedups to claim one measured cumulative gain.

Continuing the investigation

Nearly 4.9 seconds remain in this measured native request configuration. Allocation, retirement, synchronization and actual execution-flow differences remain separate attribution questions. The next experiment must preserve the successful correctness and failure gates while isolating one of those boundaries.
