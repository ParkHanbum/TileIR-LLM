Holding source, GPU kernels and checking behavior fixed, adding -O3 to the native host C++ build reduced warmed request latency by 50.829%.

5,871.735 ms reduction, 50.829%, 2.0337× speedup. This is a native-only comparison; vLLM was not rerun.

A host-only controlled change

Both arms used identical source revision af8e9db and identical CUBINs. CMAKE_BUILD_TYPE was empty in both. The only intended build difference was CMAKE_CXX_FLAGS: empty in U, -O3 in O. NDEBUG was not defined; assertions remained enabled. This is therefore not a stock CMake Release-preset comparison.

Both retained eager guard-string construction, device zero fill and guard batching. Numerical kernels, initialization ranges, checks, allocations and retirement were held fixed. Changing host compiler optimization is distinct from changing TileIR/LLVM GPU pass behavior.

Workload, correctness and lifecycle

RTX 4080, Qwen3.5-4B BF16, fixed repeated P53 prompt, B32/G16 greedy and the same native resident setup. The established request timer includes metadata/state setup, prefill/decode, CPU output IDs, request cleanup and final completion; engine/weight preparation, warmup, shutdown, comparison and log I/O remain outside.

  • All 32 requests × 512 IDs = 16,384 IDs exact.
  • Same 9,409 dispatches per request, fill and guard contracts.
  • Owned-device peak 10,912,086,708 B in both configurations.
  • Qualifier, all model children and launcher actually exited 0; independent recovery passed.

What this changes in the interpretation

The earlier unoptimized-host timings were not a fair estimate of how fast this native host implementation could run under optimization. This experiment establishes a substantial host-build effect while preserving the computation and checks. It still does not identify how much of the residual time belongs to guards, allocation, waits or other host work.

Do not compare 5,680.301 ms with an old vLLM median to present a newly measured gap. vLLM was not measured in E05. Likewise, do not multiply E02, E03 and E05 percentages into a claimed cumulative matched speedup.

Guard-string follow-up: CPU evidence only

A separate CPU source replay used 529 × 400 representative keys, corresponding to 13,542,400 checked bytes, not the exact engine-trace workload. Under -O3, that replay measured 683.27 → 13.48 ms across three CPU trials for a guard-message construction change. These figures are not native inference latency and cannot be subtracted from this experiment. The integrated engine test for that change remains pending.

Next step

Keep this optimized-host build as an explicit comparison point. Test guard-message construction as its own implementation change, preserve diagnostics and error behavior, and qualify it in the model before making any engine-speed claim.
