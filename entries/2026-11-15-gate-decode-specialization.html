2026-11-15 / kernel pilot K06 · decode gate/up specialization

Decode gate/up improves sharply.
The reference control remains faster.

The descriptor-specialized natural decode gate/up export measured a 223.232 µs median versus 705.536 µs for the deployed export, across four real weight banks. The public GemmEx control measured 175.104 µs. This is standalone screening evidence, not model integration or vLLM timing.

Two comparisons, different causal scope

deployed: manual K16 implementation
C64:      natural generic control
S64:      same natural source + exact descriptor facts
GemmEx:   specified public operation control

Deployed → S64 changes implementation AND descriptor facts.
C64 → S64 isolates the descriptor bundle within natural source.

The natural C64/S64 pair holds BM=32, BN=64, BK=64, occupancy hint 2 and launch grid 1 × 288 fixed. BF16 inputs/output, FP32 accumulation, round-to-nearest conversion and int64 indexing remain fixed, with the same 15-parameter ABI. The deployed manual implementation is not a same-source control for this specialization.

C64 matches the historical SASS evidence while debug metadata differs. That distinction is not complete binary identity and does not justify attributing a performance difference to an ABI label or metadata alone.

What the caller must supply

The logical operation is Y = A × Wᵀ for M=32, N=18,432 and K=2,560. Specialization relies on exact shape/element-stride facts and verified 16-byte alignment of the live payload/view, not just the owner allocation. The qualified source and actual descriptor manifest define the dispatch contract; reject mismatched views instead of silently overriding it.

The benchmark uses actual weight banks from layers 0, 8, 16 and 24, with the same captured layer-0 activation A0. These are four real weight banks, not four layers' actual activation inputs. Generalization to other activations, layouts or model requests requires separate evidence.

Exact timing and error-observation boundary

per bank: start event → one GEMM API enqueue → stop event
repeat for four independent Y outputs, without intervening sync or copies
end of pass: explicit stream synchronization
             → four event-end waits / elapsed queries
             → four full-Y checks + A / all-W invariance / guards

Host preparation, mode/metadata setup and poisoning are outside the event envelope. Stream elapsed time can still contain submission gaps; it is not GPU-busy time. A latent CUDA failure can be observed after four independent enqueues rather than at the runtime's per-call boundary. There is no Y consumer during that pass, and the runtime itself is unchanged. A row is accepted only after its whole pass validates.

Weight order is fixed at layers 0/8/16/24. The 360 MiB weight set, full readbacks after each pass and poisoning can perturb residency. This is not a strict cold-cache or cache-neutral experiment. The inferential units are eight paired blocks, not 32 independent replicates per arm.

The public control is cuBLAS version 130101, math mode 0, host pointer mode 0, FP32 compute type 68, algorithm 99 and BF16 dtype 14. Alpha=1, beta=0, opW=T/opA=N, leading dimensions K/K/N, the same explicit stream and default workspace (no explicit workspace configuration) were used. These settings describe the control, not a vLLM dispatch.

Validation and actual execution

The experiment accounts for 224 logical calls: 32 qualification GEMMs, 32 unchanged-SiLU checks, 32 warm GEMMs and 128 timed GEMMs. There were 176 direct TileIR calls and 48 public API calls; the latter is not the vendor GPU-launch count. Raw Y is checked before the unchanged common SiLU path, and raw Z is checked afterward. Evidence includes 128 Y/Z pair metrics and 32 first-repeat raw files totaling 28,311,552 bytes, independently verified. Subsequent repeat/warm/timed outputs were checked in child memory with SHA records, not all saved as raw files. Actual exits and independent recovery passed. The event census recorded eight creates/destroys, 256 records, 32 pass synchronizations and 128 event waits/elapsed queries.

The asynchronous validation used four independent outputs and checked errors at pass boundaries. That supports the exercised benchmark sequence; it does not establish the inference runtime's complete asynchronous ownership, reuse, completion or error-reporting semantics.

Sample evidence and screening rule

The 128 chronological timed rows retain measured index, block, arm position, bank, layer and event milliseconds from the independently verified sealed record. The table above uses pooled descriptive medians. The primary 68.3880644% result is instead the median of eight per-block reductions, with each arm's four bank timings summarized by their median within its block before forming that block's reduction.

The predeclared screen required at least a 10% reduction, favorable direction in at least seven blocks and improvement in every bank; this candidate passed that screen only. First-four versus last-four median-block drift was −0.056693% deployed, −0.207855% S64, +0.025672% C64 and −0.086855% public control. These observations do not establish independent-run reproducibility or model benefit.

Applicability, risk and next test

Keep two questions separate: whether the descriptor-qualified natural kernel is correct and competitive for these fixtures, and whether replacing the model's decode gate/up improves a complete request. This screening result supports investigation, not automatic promotion.

Before integration, preserve the exact descriptor gates and output conversion/activation contracts. Validate real caller lifetimes and unsupported-view rejection, then compare the model with only this module changed. Do not multiply this pilot with earlier down or prefill gains, or infer a new native-vLLM gap.

Reproduction status

The public summary fixes the experiment's shape, tiling, precision, bank provenance and checks. Full public replay still requires the qualified sources/artifacts, complete descriptor manifest and captured fixture; no unverified command is provided. See evidence availability.
