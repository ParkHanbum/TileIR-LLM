2026-11-14 / runtime experiment E11 · gate/up prefill S64 integration

Change only prefill gate/up.
Measure the whole native request.

One native OFF/ON/ON/OFF pilot measured a 335.516425 ms reduction in pooled request median: 4,854.503402 → 4,518.986977 ms (6.91145%). Only the prefill gate/up module selection changed. This is separate from both standalone kernel timing and untimed model qualification.

No fresh vLLM timing is included. The vLLM golden reference checks generated IDs; it is not a newly measured reference runtime. This result is not a combined gain with decode-down specialization or scratch pooling.

The operation is BF16 Y = A × Wᵀ, with M=1,696, N=18,432 and K=2,560. A is [1696,2560] with element strides (2560,1), W is [18432,2560] with (2560,1), and Y is [1696,18432] with (18432,1). Qualified S64 requires exact shape/stride facts and 16-byte-aligned live view addresses. The descriptor contract documents BF16 I/O, FP32 accumulation, round-to-nearest output and the 32-valid-row final tile.

Check the actual owner payload plus view offset and extent before specialized dispatch. Owner alignment alone is insufficient; reject a mismatch rather than overriding the contract. This timing study does not establish a general fallback for unsupported layouts. ON's safety-check cost remains inside the request measurement.

The model comparison switches the existing production export to S64. It is not the earlier same-source C64/S64 descriptor ablation, so the request-time change cannot be assigned solely to one descriptor field or to the standalone static register/stack differences.

Workload and timer boundary

RTX 4080; Qwen3.5-4B BF16; B32/P53/G16 greedy generation with the same input fixture and weights. The 16 generated tokens per sequence comprise the first output token plus 15 decode steps. Reported request times cover the whole 32-item batch, not single-prompt latency. Four actual sequential processes ran OFF0, ON0, ON1, OFF1. Each ran 2 warmups and 6 timed requests.

Adjacent-block median changes were −6.565% and −6.900%; same-arm drift was +0.684% OFF and +0.323% ON. ON was lower in all 12 positional comparisons in this pilot, with observed reductions ranging from 3.88% to 9.52%. This is one run, not a statistical confidence interval or a guarantee about future samples. Minima/maxima are observed bounds.

What actually executed and passed

  • 32 requests including warmups × 512 = 16,384 generated IDs exact against the fixed vLLM golden reference.
  • 9,409 dispatches per request, with the timed generation and checks otherwise retained.
  • ON: 32 S64 prefill launches per request, 256 per process, and 257 resource queries including startup. Queries and successful launches are separate counts.
  • Recorded fill, guard, transfer and weight invariants passed.
  • The launcher, all four children and independent recovery actually exited 0. A frozen independent CPU verifier also exited 0 after rechecking the raw IDs, counts and invariants.

The separate correctness qualification's full/chunk/tail hashes remain untimed evidence. Their absence from the timed path does not mean the measured request was unchecked: ID comparison occurs after timing, while required safety checks remain in execution.

Applicability and next test

This pilot supports a native request improvement for the qualified gate/up prefill substitution on this fixed fixture. It does not establish a speedup for every prompt, batch, GPU, cache state or output length. The tested exact-shape dispatch contract must remain explicit.

Do not multiply this gain with the down-only model result: they are separate runs and the other specialization was OFF. A combined implementation needs fresh correctness checks and timing. A new cross-runtime statement requires a matched native-vLLM checkpoint.
