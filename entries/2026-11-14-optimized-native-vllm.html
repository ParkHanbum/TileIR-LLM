The measured gap is now 8.43×.

A fresh matched N,V,V,N experiment compares the current optimized native engine with vLLM again. Native warm request time is 4,139.938 ms versus 490.951 ms for vLLM: 8.4325× longer for this fixed workload.

Same request, serial engine blocks

NVIDIA RTX 4080; Qwen3.5-4B with the same checkpoint and BF16 precision; batch 32, 53 prompt tokens per row, 16 greedy generated tokens per row. Each request produces 512 IDs. Weights remain resident and independent requests do not reuse computed prompt results. Native and vLLM processes run serially, not concurrently on the GPU.

The native prepared-launch source identifier is 31183001, using the guarded implementation described in E07. Host compilation uses -O3; this is not removal of the dynamic ownership, offset or ABI checks, guard checks, or completion fences. The reference uses official vLLM 0.32.0 and torch 2.13.0+cu130 artifacts. Package-provenance evidence and its limits are documented in audit A01.

Make the reference memory control explicit

V0 and V1 used separate fresh caches. The public vLLM setting kv_cache_memory_bytes=3,849,752,781 was fixed for both reference blocks. The audited layouts matched: 222 actual KV blocks (7,104 tokens), with 221 free after retirement. The required workload capacity was 128 blocks.

This is a vLLM-only reservation control, not proof of identical memory reservation or allocator behavior in the native engine. Capacity accounting alone is not proof that no timed preemption occurred: timed-request preemptions were not directly counted.

Explicit configuration limits

Chunked prefill was explicitly disabled to retain the fixed single-P53 experiment. Both reference startups emitted the same warning: Qwen3.5 does not officially support disabled chunked prefill. This is an intentionally configured fixed-workload comparison, not an all-defaults benchmark or evidence of broad compatibility with that setting.

Both reference logs also reported casting some FP32 normalization weights to BF16. Precision configuration should therefore be read together with those actual conversion logs, not as a claim that every original parameter already had the same storage dtype. V0 and V1 each spent 16.92 seconds compiling outside the request timer; this benchmark does not include cold-start compilation latency.

Observe dispatch without timing the observer

A V2 observer recorded one prefill dispatch in NONE mode and 15 decode dispatches in FULL mode on warmup request 0. That observation was outside timing. The observer was removed before warmup request 1 and was absent during all timed requests.

This checks the exercised warmup configuration. It is not a per-step trace of every timed request and does not establish general absence of dispatch variability or preemption.

What changed in the claim

The defensible current statement is: on this fixed resident BF16 B32/P53/G16 request, the measured optimized native path took 8.4325× the vLLM request time, with exact generated IDs. This is neither numerical-kernel-only performance nor broad model-serving parity.

The original competitive GEMMs, slow engine article and its host-build correction remain intact as dated evidence. Intermediate native-only experiments explain tested changes, but their medians come from separate runs and must not be chained into a synthetic comparison. This fresh experiment supplies the new end-to-end reference point.

A substantial gap remains. The next comparisons should isolate execution-flow boundaries while preserving the current correctness and failure checks. Neither this timing nor the older diagnostic trace proves which remaining component accounts for that gap. The older trace was not paired with this experiment.
