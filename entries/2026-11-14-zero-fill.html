2026-11-14 / experiment E03

Initialize the same bytes.
Stop shipping host zeros.

A native-only, one-factor experiment replaced host-generated zero buffers and H2D copies with device memset for fresh allocations. Warm median request time fell by 17.11%.

The measured result

ArmPooled timed median
H · host zeros + H2D14,012.940 ms
D · device zero fill11,615.782 ms

2,397.16 ms less per request: 17.11% reduction, 1.206× speedup. Both arms enabled the previously validated guard batching. This is a separate H,D,D,H experiment, not a new native-vLLM comparison.

Do not subtract these medians from E01 or E02, or multiply their speedups to claim a measured cumulative improvement. The native baseline was remeasured here; vLLM was not.

Exactly what changed

H: allocate fresh owner → host zero buffer → H2D zero chunks
D: allocate fresh owner → cuMemsetD8_v2(payload, 0, size)
                         │
             existing upload-complete fence
                         │
               unchanged numerical launches

The candidate changes only zero fill of a newly allocated owner that has not been exposed to any numerical launch. A default-stream memset does not automatically order against an already running non-blocking compute stream. Restricting the operation to fresh owners and retaining the existing upload-completion fence avoids silently relying on that ordering.

Memory allocation and retirement, guard checking, numerical kernels, request-state initialization scope and byte counts were unchanged. The test does not disable initialization or relax the memory checking contract.

The byte count is cumulative work over a request, not simultaneously resident memory. Measured owned-device peak was 10,912,086,708 B in all four blocks; minimum observed free memory was approximately 4.198–4.208 GB. Removing these host-zero copies does not eliminate all H2D transfers: prompt, metadata and other required transfers remain. Driver memset is also not a model numerical TileIR kernel; no claim is made that the physical GPU activity census is unchanged.

Measurement and correctness

Native-only H,D,D,H serial blocks, each with 2 warmups and 6 timed requests, using the fixed RTX 4080, Qwen3.5-4B BF16 B32/P53/G16 workload. All 32 requests × 512 generated token IDs matched the reference. The numerical kernels, guard-batching policy, allocation and retirement behavior were held fixed. Initialization and warmup are outside the request timer under the existing measurement contract.

Preserved contracts and qualification

Both arms retained 441,216 canary items / 14,118,912 B, 528 finite-validation calls and 8,881 numerical calls per request. Generation-stage weight I/O remained zero. Before model measurement, the GPU qualifier exercised 6 contexts, 60 payload/canary comparisons and 4 negative cases. API-error paths were tested with CPU mocks only, not injected Driver failures on the GPU.

Six GUI processes were present. Physical device operations internal to Driver memset were not censused. General EOS support is not asserted. Summary statistics and method are published here; full raw samples and the public replay bundle remain subject to the evidence availability limits.

What it explains, and what it does not

This experiment identifies zero-initialization implementation as another material cost in this native runtime. It does not prove that device memset alone accounts for all remaining latency, or that vLLM performs the same initialization sequence. It also does not measure the isolated cost of allocation, retirement or GPU synchronization, because those behaviors were held fixed rather than removed.

Next boundary

Continue separating request-lifetime allocation and retirement from waits for GPU work. Host API intervals may contain waiting for prior device work, so adding those intervals to kernel time would double-count it. Keep traces separate from unprofiled performance runs, and preserve the correctness gates.
