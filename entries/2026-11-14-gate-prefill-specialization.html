2026-11-14 / kernel pilot K04 · gate/up prefill specialization

A prefill export changes sharply.
The evidence is still one bank.

For one actual historical gate/up prefill input bank, descriptor specialization brings the tested TileIR operation envelope close to the cuBLAS GemmEx control. The result is standalone evidence, not model-level performance or general cuBLAS parity.

This is Track A: kernel qualification. The tested shape is BF16 M=1,696, N=18,432, K=2,560 on an RTX 4080. Only one historical A/weight bank was measured; other banks and cache regimes are untested here.

Concrete C64 → S64 descriptor change

The same-source comparison changes what the compiler is allowed to know about each array, not the mathematical operation. The stored weights are W[N,K]; the result is Y = A × Wᵀ with A[M,K] and Y[M,N]. No physical transpose of W is implied.

ArrayS64 exact shapeS64 exact strides (elements)Verified view-base alignment
A[1,696, 2,560](2,560, 1)16 bytes
W[18,432, 2,560](2,560, 1)16 bytes
Y[1,696, 18,432](18,432, 1)16 bytes

C64 has dynamic shape and stride fields and only a base-address divisibility promise of 1. S64 uses the exact manifest tuples above and a verified base-address divisibility of 16. The following is explanatory ArrayConstraint-style pseudocode, not a replacement implementation; unshown options are preserved rather than assigned new defaults.

# For each of A, W and Y:
# C64 source descriptor checked by the specialization wrapper
assert source.shape_constant is None
assert source.stride_constant is None
assert source.base_addr_divisible_by == 1

# S64 export descriptor; keep the other options unchanged
specialized = ArrayConstraint(
    **other_unchanged_options,
    index_dtype=ct.int64,
    shape_constant=manifest_shape,
    stride_constant=manifest_strides_in_elements,
    base_addr_divisible_by=16,
)

The wrapper explicitly sets S64 indexing to int64. C64's int64 identity is established by the original ABI/ELF evidence, not inferred from that wrapper assertion. The public field definitions can be checked in the tagged cuTile v1.7.0 ArrayConstraint source. This tag is a documentation reference, not a substitute for the experiment's artifact provenance.

Strides are not byte alignment

A stride tuple maps logical indices to offsets in elements. For BF16, element offsets are multiplied by 2 to obtain byte offsets. The actual view pointer is owner_payload + byte_offset; checking only the allocation base is insufficient. A +2-byte view offset is the negative alignment case: it violates a 16-byte promise even if the underlying owner is aligned.

element_offset(i, j) = i * stride[0] + j * stride[1]
byte_address(i, j)   = view_pointer + 2 * element_offset(i, j)
required: view_pointer % 16 == 0

Unit stride does not mean that every BF16 element is 16-byte aligned. It describes contiguity. TileIR 13.4's div_by specification explains the distinct divisibility contract, including tensor-view base addresses. That semantic reference does not by itself prove a particular emitted instruction or lowering pipeline.

Practical export and dispatch checklist

  1. At export, verify and record the exact A/W/Y shape and element-stride facts before constructing the specialized descriptors.
  2. At runtime, validate each actual A/W/Y view: its owner is live, its byte extent is in bounds, its dimensions and strides match the export, and its payload-plus-offset pointer satisfies 16-byte alignment.
  3. On any mismatch, do not dispatch this specialized kernel. Reject the call or route through a separately qualified general fallback, if one exists. This article does not establish that such a fallback has been integrated.

What stays fixed

Within this C64/S64 experiment, source computation, tile 64 × 128 × 64, occupancy hint 2, other hints, BF16 inputs/output, FP32 accumulation and explicit BF16 round-to-nearest conversion remain fixed. The actual ELF records retain the same v2 int64 launch ABI with 15 parameters of 8 bytes each. Static descriptor facts do not imply that launch parameters were removed.

The separately measured Current arm is not the same-source control; descriptor attribution uses C64 versus S64, not Current versus S64.

With M=1,696 and a 64-row tile, the last M tile has 32 valid rows. The source padding and boundary-handling behavior stays unchanged; specializing the shape does not grant permission to load or store invalid rows.

Why this can help, and what still needs isolation

Compiler-opportunity hypotheses: known dimensions and strides may simplify address expressions and boundary predicates; verified alignment plus contiguous access may enable fixed-width vector access or different data movement. These are reasons to test specialization, not observations that a specific vector instruction, transfer mechanism or compiler pass was selected.

A planned same-source ablation would vary static shape, exact stride and verified alignment one at a time, retain identical fixtures/ABI/tile/numerics, and repeat both correctness and timing checks. Only that controlled evidence can separate individual contributions from their interactions. The existing result establishes the bundle, not a percentage attributable to any single fact.

Timing contract and reference settings

Eight balanced Williams-order blocks measured all four arms on one reused actual bank, with two warmups per arm. Each sample is one prevalidated same-stream GEMM bracketed by start/end events. SiLU was not timed, and no empty-operation subtraction was applied.

outside: preparation / initialization / upload / mode / owner checks
inside:  start event → one same-stream GEMM → end event
outside: synchronization / D2H / hash / guard checks

Host submission gaps can contribute to the envelope. Readbacks between calls, cache state and desktop GUI activity can perturb measurements; the ranges do not remove these limitations.

The public GemmEx control reports cuBLAS version 130101, BF16 input/output dtype 14, FP32 compute type 68, math mode 0, host pointer mode 0, and algorithm 99. Alpha=1, beta=0, opW=T, opA=N, leading dimensions K/K/N, the same explicit stream and default workspace pool were used. This is a specified cuBLAS control, not identification of vLLM's chosen kernel.

Accuracy before timing

Eight GEMM correctness calls and eight calls through the same unchanged SiLU path passed exactness, finiteness, repeat and 32-row-tail checks. Eight warm and 32 timed calls also matched exactly: 56 calls total. Actual exits and independent recovery passed. The diagnostic as a whole took 27.218 seconds; that includes diagnostic work and is not model inference speed.

Correctness is scoped to this fixture and its tested tail, repeat and activation path. It is not proof for all shapes, arbitrary strides or all activation distributions. A specialized runtime dispatch must continue to validate the descriptor assumptions.

Separate model qualification: gate/up prefill only

This section reports correctness qualification, not model timing. The standalone event measurements above remain a different experiment. This qualification ran the actual Qwen3.5-4B BF16 B32/P53/G16 greedy fixture on RTX 4080 through the direct tileir-first-token engine path.

The fixture, weights, other operation paths and greedy generation contract remain unchanged; reference outputs are used to check results, not injected into execution.

What exactness means here

Token IDs were compared exactly. The intermediate evidence consists of matching fingerprints over the recorded tensor regions. Those matches support agreement at the tested boundaries, but they are not a stored-tensor byte-by-byte memcmp and do not independently prove equality for every possible tensor or workload. Hash records, invariance checks, dispatch counts and actual exits answer different questions; none should substitute for the others.

The tested fixture covers these 32 prefill layers and their observed downstream generation. It does not establish correctness for other batch sizes, prompt lengths, layouts, weights, precision modes or stopping behavior. A caller whose descriptors do not satisfy the checked contract must not dispatch this specialized export.

How an engine developer should use this result

This qualification supports proceeding to a separately controlled model-timing test of this one dispatch substitution, with decode-down specialization and pooling still explicitly controlled. It does not establish a request-speed gain. To reproduce the qualification, an implementer needs the exact fixture and model/config identities, both selected export artifacts, live-view checks and the same boundary fingerprints/ID comparison criteria. Complete public replay artifacts and verified commands are not supplied in this section; see evidence availability.

No model-time measurement is reported here. Do not multiply the standalone S64 gain into an inferred token-generation speedup or compare it with a historical vLLM request time.

Separate follow-up: the subsequently verified native gate/up prefill model A/B measures whole-request timing with diagnostic readbacks disabled in both modes. It is separate from this correctness qualification and the standalone pilot.

Standalone timing limits and next boundary

These timings describe the measured operation envelope, not a claim of pure GPU compute time. Cache effects beyond this single-bank setup were not tested. The standalone pilot alone establishes no engine-integration outcome, end-to-end token-speed result or matched vLLM request measurement. The separate model qualification above adds correctness evidence only.

The next qualification boundary is broader fixture/layout coverage and a valid integration contract, followed by a separate matched end-to-end checkpoint. The previous down-projection specialization is another operation and another experiment, not an additional speedup to multiply into this result.
