Correction to interpretation, not a replacement measurement. The native executable used in the original 27.61× comparison had no host C++ optimization flag. The matched request times remain measurements of the configurations actually run; they are not an optimized-native versus optimized-vLLM host comparison.

What the build audit verified

The original native revision afc78b9 was tied to its exact executable SHA and recorded compile artifacts. CMAKE_BUILD_TYPE and CMAKE_CXX_FLAGS were empty. The graph target's actual host C++ flags included -std=c++17 -Wall -Wextra -Werror, with no -O option. The latest zero-fill experiment and the diagnostic trace below used the same unoptimized host-build configuration.

This finding concerns the native host C++ executable. It does not establish that the separately compiled TileIR GPU kernels were unoptimized. At the time of this audit, a host-optimization comparison was being prepared. The subsequent E05 result isolates -O3 without using a Release preset.

How to read the earlier result now

The original native/vLLM pooled medians remain 13,527.36 versus 489.93 ms for the measured configurations. The approximately 27.61× ratio is not retracted or silently changed. Its interpretation is narrower: it includes an unoptimized native host build, extensive checking and a different graph policy. It cannot measure the residual gap after optimizing the native host compiler configuration.

The earlier native-only guard-batching and zero-fill A/B results also remain scoped to their tested builds. A host-build correction does not retroactively turn their timings into optimized-engine results.

The whole interval contained 8.735 s with no observed GPU activity. Of that, 6.526 s was outside observed CUDA API intervals. Region totals and the whole interval need not match exactly because their boundaries differ and values are rounded.

Trace completeness warning: Nsight reported “Not all CUDA/NVTX events might have been collected.” Key counts matched, but that does not prove the trace is complete. “No observed GPU activity” is therefore not proof that the GPU was idle, and time outside observed CUDA APIs is not yet a resolved CPU-cost attribution.

A source-level hypothesis to test

Inspection found eager std::string construction in guard checking over a reported 13,454,656-byte checking span. In an unoptimized host build this is a plausible cost candidate. The source pattern alone does not quantify its runtime contribution or prove it explains the trace gaps.

This byte count describes the specific guard-source observation. It must not replace the separately reported aggregate 14,118,912 canary bytes per request in the earlier guard experiment.

Next discriminating experiment

  4. Compare unprofiled matched warm request times; do not reuse the 11.468 s diagnostic capture as a baseline.
  5. Only after that comparison, isolate remaining host logic and synchronization costs.
