2026-11-14 / diagnostic D01 · forward path and GEMM scope

Audit the GEMM that actually runs.

The older competitive standalone GEMMs do not exonerate the current engine's GEMMs. The production gate/up shape, tiling, ABI and recorded layout facts differ. We need a same-workload comparison before attributing the remaining gap.

Scope correction: the earlier standalone results remain valid for those measured kernels. They do not prove that today's native forward path has comparable GEMM performance. This diagnostic adds no new production benchmark or native-vLLM ratio.

The actual traced current gate/up calls averaged 11.517 ms for prefill and 714.780 µs for decode. Those averages are neither the older standalone medians nor a matched comparison against the older kernel: shape and execution details differ.

The current export also records weaker layout facts. Whether that affects generated code or performance is still unknown. An ABI difference is not evidence of a slowdown by itself, and an old ABI-v1 kernel cannot simply be substituted into an ABI-v2 call.

Required next comparison:
  same M / N / K, input dtype and checked layout
  + equivalent output and accumulation contract
  + compatible launch ABI and ownership checks
  → compare actual exported kernels under matched conditions

Do not infer:
  old N=9216 standalone result → current N=18432 GEMM parity

An actionable same-shape case: decode down-projection

Decode down-projection does match logically at M=32, N=2,560, K=9,216, but the implementations still differ. The current manual tile is 32 × 64 × 64 with four K16 slices and 208 registers. The older independent natural implementation uses a 32 × 64 × 128 single full tile with occupancy setting 1.

The saved native trace observed approximately 678 µs per current call (325.545 ms over 480 calls). The older synthetic four-bank natural measurements were 75.872–76.135 µs. Those numbers have different measurement scopes, methods and CUBINs. They are not a same-run speedup ratio and do not guarantee that the older candidate will retain its performance in the current engine.

This gives us a concrete next comparator: preserve the same M/N/K and verified layout, adapt the launch contract correctly, then check numerical results and measure both exports under matched conditions. It is more informative than substituting an old standalone result for a production measurement.

Why there is no paired vLLM trace yet

The attempted reference trace was blocked before import by the experiment wrapper with preload not permitted. This is not a vLLM crash and provides no evidence about its forward execution performance. Older vLLM traces, from different configurations, cannot stand in for the missing matched trace.

What this changes in the investigation

Native forward regions now deserve direct attention, including the actual GEMM exports. We must compare their logical work, checked layouts and generated kernels rather than ruling them out using a different standalone control. This is an attribution correction, not a claim that GEMM explains the entire gap or that a particular tiling will fix it.

The first article now carries an explicit measured-scope note; its original numerical snapshot is preserved. The last matched native-vLLM result remains E08. No timing-series data is added for this diagnostic.
