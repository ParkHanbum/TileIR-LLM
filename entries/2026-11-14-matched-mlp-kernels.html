2026-11-14 / kernel pilot K02 · same-shape three-arm comparison

Same shapes. Real weights.
The candidate is not a general win.

A three-arm MLP kernel pilot compares the current TileIR export, a candidate TileIR export and a cuBLAS GemmEx control on the same inputs. Candidate effects are mixed, and both TileIR implementations remain substantially slower than this cuBLAS control in the measured cases.

This is Track A: isolated kernel qualification and benchmarking, not a production runtime result. No candidate is promoted on this evidence, and no whole-engine speedup or new vLLM ratio is claimed.

What was held equal

NVIDIA RTX 4080, sm89; BF16; identical measured A, weights and output workload for each arm. Shapes are the actual merged gate/up and down-projection shapes, rather than substituting the earlier half-width gate/up control.

The input activations are from layer 0. The real weight sets are from layers 0, 8, 16 and 24. This is not a replay of each layer's true activations: rotating the weights while retaining layer-0 A changes the data-access control, not the provenance of A.

The cuBLAS control uses GemmEx with its default workspace on the same stream. It is not proof of the algorithm or kernel selected by vLLM. No live profiler was used. The reference was cuBLAS 13.1.1.3 (reported version 130101), BF16 inputs/output with FP32 compute (compute type 68), math mode 0 and algorithm 99. Host-pointer alpha=1 and beta=0, opW=T / opA=N, and leading dimensions K/K/N were recorded; the default workspace pool was used.

The candidate improves single-weight decode down but regresses its rotation case. Decode gate/up reverses direction: slower for single weights, faster for rotation. Prefill gate/up is slightly slower in both displayed regimes. A selected favorable cell cannot justify general promotion.

What the event envelope includes

same nonblocking stream:
  start event → unchanged typed TileIR launch or GemmEx → stop event
  existing output-read synchronization → event query

Initialization, A/weight preparation, output reads, guards and logging are outside the event envelope. Host bookkeeping can still contribute submission gaps between recorded stream events; these timings are not guaranteed to be pure kernel execution. Output D2H reads between invocations can perturb cache state even though the copies are outside the event envelope.

Pilot execution and correctness scope

The pilot used 2 warmups and 6 balanced Latin-order timed blocks. There are 6 single-weight samples and 24 rotation samples per arm and shape. These are not independent-sample confidence intervals: the displayed bounds are observed minimum and maximum values. All three shapes across all four weight sets passed fresh reference-repeat and qualified three-way raw-output comparisons, with unchanged SiLU/chain checks. All 90 warm and 270 timed outputs were exact under the qualified checks; all 12 fresh shape/weight gates passed. Across the 71 recorded metric pairs and 560,873,472 compared elements, raw mismatches were zero. This supports bitwise equality within these recorded qualified comparisons on the tested fixtures, not universal equivalence. The experiment accounts for 456 logical operations: 312 TileIR calls and 144 cuBLAS calls. Normal exits and independent recovery passed.

An earlier 3 × 5 exercise was an accuracy-only raw-output exactness check. It supplies no performance result. Neither the earlier exactness check nor this pilot establishes equality for untested inputs, shapes, algorithms or precision modes.

Interpretation and next boundary

The same-shape test confirms that the older standalone controls cannot clear the actual current exports of performance responsibility. It also rejects the simple assumption that this candidate improves all cases. These measurements do not identify the entire cause of the cuBLAS gap or prove a particular tiling, register count or layout annotation is responsible.

Further kernel work needs matched layouts, numerical contracts and repeatable timing before integration. Runtime-flow work can continue independently, but only a new matched end-to-end checkpoint can establish their combined request-level effect.
