2026-11-14 / runtime diagnostic D02 · execution envelopes

Follow the execution boundaries.
Do not add overlapping clocks.

A no-injection native/vLLM diagnostic records request phases and same-stream event envelopes. It narrows where to inspect the runtime flow, but the engines' asynchronous delivery boundaries are different. These numbers are not a new performance ratio.

This is Track B: runtime execution-flow evidence. The last production, unprofiled matched comparison remains E08. Do not replace its measurement with this instrumented diagnostic.

Run and correctness scope

Each engine ran two warmups and one captured request using the fixed B32/P53/G16 workload. Each generated its own tokens; no reference decode tokens or intermediate tensors were injected. All 1,536 generated IDs per engine matched the tested reference exactly.

The native capture recorded 9,409 launches and used the exact prior numerical kernel build. vLLM recorded 16 actual forward invocations: one NONE prefill with 1,696 input tokens and 15 FULL decode forwards with 32 input tokens each. Actual child and outer-launcher exits were 0, and independent recovery passed.

These are diagnostic captures, not repeated production timing samples or general correctness coverage across prompts and stopping conditions.

Same-stream event envelopes

The following sums group prefill and decode event intervals on the relevant execution stream. They are interval envelopes, not a GPU-busy census or isolated numerical-kernel times. Submission gaps and stream dependencies can contribute to an elapsed envelope.

The native forward event spans only the 32-layer loop. Native endpoint spans final normalization, prefill-only last-token gather, tied-embedding LM head, BF16-to-FP32 cast, finite-failure check, greedy selection, token D2H, and guard/scope-retirement work. The 32 host int64 IDs are checked against the vocabulary bound of 248,320. These are not isolated LM-head timings.

The vLLM forward interval uses the original forward_start to finish_forward boundaries. Its sample_tokens interval encloses the separately recorded sampling compound (gather, LM head and greedy selection), which wraps the original V2 runner.sample(). The compound is nested, not an additional cost to add to sample_tokens, and does not isolate the head alone.

Native endpoint and vLLM sampling compound are therefore not interchangeable algorithms or boundaries. The forward observations motivate inspection of actual layer flow; they do not isolate a particular cause.

The native input-feedback region totals 3.604 ms across all 15 decode steps. This is not prefill input preparation, the entire copy pipeline, or every synchronization involved in feedback. It must not be used to subtract all transfer costs from the request.

The output-copy event starts before the original copy-stream wait and includes the main-stream producer dependency. It is not a measurement of DMA payload time alone. Host consumption through get_output includes the original completion-event wait and overlaps other execution/delivery work. These rows cannot be added to forward or sampling times, or to each other, to reconstruct the request total.

Next: compare real layer flow

The positive next step is to inspect MLP and Gated DeltaNet layer execution together with submission behavior: which operations are issued, how their contracts line up, and what dependencies separate them. The same-shape MLP kernel pilot addresses a separate kernel-level question; it does not assign a share of these runtime envelopes to any cause.

This capture supports a focused investigation, not certainty about how much of the remaining difference comes from kernels, host submission, synchronization or runtime structure. A change still needs correctness gates and a fresh matched measurement before a speed claim.
