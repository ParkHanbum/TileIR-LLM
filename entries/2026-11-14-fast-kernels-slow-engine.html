A few fast matrix multiplications did not add up to a fast inference runtime. This contrast is the starting point of our TileIR-LLM performance investigation.

Two true results, two different questions

On RTX 4080 with BF16, selected standalone TileIR GEMMs matched or slightly beat a PyTorch matrix-multiplication reference. Later, the native C++ engine took 13,527.36 ms per warmed fixed request versus 489.93 ms for vLLM: 27.61× slower. Both observations are valid, but they are not measurements of the same scope.

What the GEMM reference actually was

torch.mm(A, W.T, out=C) computes the same matrix product from matching BF16 inputs and weights into a preallocated output buffer. Preallocation avoids timing a new output allocation in the comparison. We compare this call with our replacement TileIR GEMM. This is not a complete model run, and does not establish that the exact same reference kernel is selected inside vLLM.

What the 28× number includes

The native/vLLM comparison used the same Qwen3.5-4B checkpoint and fixed BF16 workload: 32 rows, 53 input tokens and 16 generated tokens, greedy. Resident weights and warmed engines excluded startup. Request state preparation, execution, final CPU IDs and request cleanup/completion were included. N,V,V,N process blocks each used 2 warmups and 6 timed requests; all 16,384 output IDs matched and all processes exited 0.

vLLM actually used FULL_AND_PIECEWISE CUDA Graph mode; native did not. Native also retained extensive finite, bounds and canary validation. These differences are part of the measured implementation, not hidden qualifications. Read the paired experiment.

Our working inference, not a verdict

The tested GEMMs do not reproduce the huge request-time gap. Runtime execution flow is therefore a strong investigation target. This does not prove all GPU kernels are equally fast, nor that the remaining gap is entirely CPU overhead.

We still need to distinguish GPU work from waiting for it; launch count from launch cost; and allocator work from synchronization hidden inside allocation or retirement. We must also compare real prefill/decode paths rather than assuming a standalone GEMM covers the model.

First controlled change: preserve checks, batch reads

A separate native-only A/B replaced many individual guard-copy submissions with batched submissions at the same checking boundaries. Checked bytes and numerical kernels were unchanged. Within that experiment, median request time fell from 15,148.30 to 13,847.13 ms (−8.59%); 16,384 tokens remained exact.

This establishes a useful runtime improvement, not the full explanation of the vLLM gap. The A/B baseline differed from the earlier paired run, so the two improvements must not be chained. vLLM was not remeasured. Inspect the guards experiment.

How this becomes useful to other implementers

We will publish the measured path, the exact hypothesis, the one-factor change, its correctness tests and its matched result. Analysis of vLLM is grounded in its public implementation and observed behavior. An optimization found in our engine is not automatically an optimization vLLM uses. Failure, non-improvement and unresolved attribution belong in the log too.

Next questions are fresh-buffer zero fill, request allocation/retirement, synchronization, and separate prefill/decode flow. No zero-fill outcome is claimed here. Reproducibility status and evidence requirements.
