2026-11-14 / experiment E02

Keep the checks.
Batch the submissions.

The first isolated runtime change reduced warm request time by 8.59%, but left most of the observed latency unresolved.

Exactly one change

A reads prefix/suffix canaries using individual 32-byte D2H copies. B submits the same reads at the same guards() boundary with cuMemcpyBatchAsync_v2, waits for completion, then checks the bytes in the same CPU order. B prepares a 64 KiB pinned diagnostic arena. Uncertain submit/completion failures quarantine resources rather than retrying unsafely.

The preceding completion fence, retirement guard_one, numerical kernels, device allocation, checked bytes, state reset, weight residency, EOS contract and graph policy stay unchanged.

Qualification and result integrity

Before the model run: 10 contexts, 8 deliberate canary corruptions detected, 11 batches, 44 copies. CPU tests and independent review passed. A,B,B,A each ran 2 warm + 6 timed requests: 16,384 IDs exact, unchanged numerical/state/weight contracts. Qualifier, all four model children and launcher exited 0, no retries/signals; independent recovery passed.

What it proves

Reducing submission overhead at this checking boundary improved this native workload while preserving its validation contract. It does not attribute the entire native-vLLM gap, and does not prove vLLM uses this technique. GUI contention and only two processes per arm limit generalization. Physical GPU activity inside the batched Driver operation was not independently censused.
