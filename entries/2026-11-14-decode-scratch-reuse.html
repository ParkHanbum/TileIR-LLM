2026-11-14 / runtime experiment E09 · decode scratch reuse

Fewer allocations.
No defensible speedup yet.

Decode scratch reuse reduced physical allocation/free counts while preserving the tested correctness checks. Its timed OFF/ON/ON/OFF run, however, developed abrupt temporal drift. The measured medians do not support a causal performance conclusion or promotion.

This is Track B: runtime evidence. A verified resource-count reduction is distinct from a verified latency improvement. No speedup, integrated promotion or new vLLM comparison is claimed.

First gate: test the executable that actually exists

Run 01 stopped after its OFF arm because the actual executable lacked the requested feature, despite the pinned source. That run is not a valid OFF/ON comparison. Source identity alone does not prove that a binary contains the feature under test.

A fresh build at source identifier a772da5 was verified through source, translation unit, object/archive and link provenance. The actual executable's help and CPU syntax checks demonstrated the expected option. Run 02 used that same fresh binary for both OFF and ON.

The earlier failed gate was not waived or retrospectively relabeled as successful evidence. The practical lesson is to verify executable capability and build provenance before starting a long measurement, not only record a repository revision.

What reuse changes

In the dedicated validation run, physical allocation and free counts each fell from 30,412 to 27,534, a reduction of 2,878 each. That validation scope recorded 2,880 acquisitions/retirements and 2,878 reuses, with 1,769,600 bytes reserved.

The guards, zeroing and numerical kernel set were retained. Reuse is a runtime allocation/lifetime change, not permission to skip checks, retain incorrect request state or alter numerical work.

In each timed-run process, the physical allocation/free totals were 83,363 OFF versus 75,685 ON. Each ON process recorded 7,680 acquisitions and retirements, 7,678 reuses, a peak pool reserve of 1,769,600 bytes and zero reserve at close. These are process totals, not per-request counts, and must not be conflated with the separate validation totals above. Per-process logical retirement (83,032), synchronization (86,352), fill (83,363), launch (75,272), guard-copy (3,364,326) and guard-byte (107,658,432) counts were identical across modes.

Correctness evidence, separately from timing

The dedicated OFF and ON checks each matched 3 × 512 generated IDs. Full 16 × 32 down-projection hash checks covered two requests. The performance run checked 16,384 generated IDs exactly. Timed mode was token-only; full-output hashes came from the separate correctness test, not timed requests. These results qualify the tested workload and checks, not all possible lifetimes, shapes or prompts.

Run 02 used OFF/ON/ON/OFF with 2 warmups and 6 timed requests per process block. The pooled timed medians were 4,557.192 ms OFF versus 4,873.648 ms ON, an observed increase of 6.944%.

An abrupt temporal shift occurred inside ON0, and later blocks ran at a different level from the early blocks. Pooling across that shift is not a clean estimate of the feature's cost. The observed increase is not a causal regression claim; similarly, selecting the early OFF0/ON0 pair would not establish a speedup.

Balanced ordering does not automatically cancel a discontinuous time-dependent change. Without resolving or controlling the drift, neither the pooled number nor a favorable subset is enough to promote the candidate.

Keep the claims separate

  • Supported: fewer recorded physical allocations/frees with the reported reserve and reuse counts.
  • Supported within the tests: exact token/hash checks with guards, zeroing and numerical kernels retained.
  • Not established: latency improvement or a causal slowdown attributable to reuse.
  • Not performed here: a fresh vLLM baseline or a follow-up performance rerun.

The useful next step is to explain or control the temporal drift, then repeat a predeclared matched experiment while preserving the same correctness and executable-provenance gates. This is a proposed measurement requirement, not a claim that the rerun has happened.
