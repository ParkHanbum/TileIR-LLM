2026-11-14 / kernel pilot K03 · decode down descriptor specialization

Specialize the descriptor.
Keep the attribution narrow.

For one matched decode down-projection shape, a descriptor-specialized export sharply improves on the current generic export. The experiment changes a bundle of validated descriptor facts; it does not isolate one fact or prove that the ABI itself caused the gap.

This is Track A: standalone kernel evidence. No engine integration, vLLM comparison or whole-model speedup is established here.

Four arms, one logical operation

NVIDIA RTX 4080; BF16 decode down-projection with M=32, N=2,560, K=9,216. Each arm uses the same historical layer-0 activation input and real weight sets from layers 0, 8, 16 and 24. These are not the true activations of all four layers.

Concrete C64 → S64 descriptor change

The same-source comparison changes what the compiler is allowed to know about each array, not the mathematical operation. The stored weights are W[N,K]; the result is Y = A × Wᵀ with A[M,K] and Y[M,N]. No physical transpose of W is implied.

ArrayS64 exact shapeS64 exact strides (elements)Verified view-base alignment
A[32, 9,216](9,216, 1)16 bytes
W[2,560, 9,216](9,216, 1)16 bytes
Y[32, 2,560](2,560, 1)16 bytes

C64 has dynamic shape and stride fields and only a base-address divisibility promise of 1. S64 uses the exact manifest tuples above and a verified base-address divisibility of 16. The following is explanatory ArrayConstraint-style pseudocode, not a replacement implementation; unshown options are preserved rather than assigned new defaults.

# For each of A, W and Y:
# C64 source descriptor checked by the specialization wrapper
assert source.shape_constant is None
assert source.stride_constant is None
assert source.base_addr_divisible_by == 1

# S64 export descriptor; keep the other options unchanged
specialized = ArrayConstraint(
    **other_unchanged_options,
    index_dtype=ct.int64,
    shape_constant=manifest_shape,
    stride_constant=manifest_strides_in_elements,
    base_addr_divisible_by=16,
)

The wrapper explicitly sets S64 indexing to int64. C64's int64 identity is established by the original ABI/ELF evidence, not inferred from that wrapper assertion. The public field definitions can be checked in the tagged cuTile v1.7.0 ArrayConstraint source. This tag is a documentation reference, not a substitute for the experiment's artifact provenance.

Strides are not byte alignment

A stride tuple maps logical indices to offsets in elements. For BF16, element offsets are multiplied by 2 to obtain byte offsets. The actual view pointer is owner_payload + byte_offset; checking only the allocation base is insufficient. A +2-byte view offset is the negative alignment case: it violates a 16-byte promise even if the underlying owner is aligned.

element_offset(i, j) = i * stride[0] + j * stride[1]
byte_address(i, j)   = view_pointer + 2 * element_offset(i, j)
required: view_pointer % 16 == 0

Unit stride does not mean that every BF16 element is 16-byte aligned. It describes contiguity. TileIR 13.4's div_by specification explains the distinct divisibility contract, including tensor-view base addresses. That semantic reference does not by itself prove a particular emitted instruction or lowering pipeline.

Practical export and dispatch checklist

  1. At export, verify and record the exact A/W/Y shape and element-stride facts before constructing the specialized descriptors.
  2. At runtime, validate each actual A/W/Y view: its owner is live, its byte extent is in bounds, its dimensions and strides match the export, and its payload-plus-offset pointer satisfies 16-byte alignment.
  3. On any mismatch, do not dispatch this specialized kernel. Reject the call or route through a separately qualified general fallback, if one exists. This article does not establish that such a fallback has been integrated.

What stays fixed

Within this C64/S64 experiment, source computation, tile 32 × 64 × 128, occupancy hint 1, other hints, BF16 inputs/output, FP32 accumulation and explicit BF16 round-to-nearest conversion remain fixed. The actual ELF records retain the same v2 int64 launch ABI with 15 parameters of 8 bytes each. Static descriptor facts do not imply that launch parameters were removed.

Why this can help, and what still needs isolation

Compiler-opportunity hypotheses: known dimensions and strides may simplify address expressions and boundary predicates; verified alignment plus contiguous access may enable fixed-width vector access or different data movement. These are reasons to test specialization, not observations that a specific vector instruction, transfer mechanism or compiler pass was selected.

A planned same-source ablation would vary static shape, exact stride and verified alignment one at a time, retain identical fixtures/ABI/tile/numerics, and repeat both correctness and timing checks. Only that controlled evidence can separate individual contributions from their interactions. The existing result establishes the bundle, not a percentage attributable to any single fact.

Event boundary and cache caveat

event start → unchanged typed TileIR / GemmEx enqueue → event stop

This is an operation envelope, not an assumption of pure GPU execution. Metadata preparation, poisoning, guards and input/output checks are outside the event span. Post-pass readback of all weight sets can perturb cache state. The comparison does not assign the elapsed change to a particular instruction or hardware resource.

Correctness and qualification

All 232 calls were exact across the four weight sets: 32 fresh qualification calls, 40 warm calls and 160 timed calls. All passed raw exactness checks. Actual exits and independently sealed recovery checks passed. This supports the tested operation and fixtures, not all shapes, layouts or alignments.

Specialized shape, stride and alignment assumptions are part of the interface contract. They must be checked before dispatch, not silently applied to inputs that do not satisfy them. A general runtime still needs a correct path for unsupported descriptors.

What the bundle establishes, and what it does not

The controlled C64/S64 comparison establishes that this verified descriptor-fact bundle materially changes performance for this down-projection case. It does not tell us whether fixed dimensions, contiguous strides, alignment information or their interaction accounts for a particular share of the change.

The v1 arm provides historical context, not a proof that ABI v1 is inherently faster than ABI v2. Source/store behavior and constraints must be held equal in any experiment intended to isolate an ABI-related cause.

The next boundary is a qualified implementation contract, followed by explicit integration and a fresh matched end-to-end checkpoint. Neither this down-only result nor the earlier three-shape pilot proves gains for all MLP operations or for the inference engine.
